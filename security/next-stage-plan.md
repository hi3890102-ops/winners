# 다음 단계 계획 — 독립 백업 → 스테이징 검증 (2026-09-20)

기존 런북(`new-staff-self-profile-runbook.md`)의 순서·복구 절차를 **반복하지 않고**, 이번에 확인·추가된 것만 적습니다. 이 문서는 승인 요청 전 정리이며 어떤 변경도 실행하지 않았습니다.

## 1. 읽기 전용으로 확인한 사실 (2026-09-20)

| 항목 | 운영 `staff`(bhwuuxcr…) | 스테이징 `manee-staging`(obpkzecg…) |
|---|---|---|
| DB 크기 | 83 MB | 14 MB |
| 매장 / 직원 / 계정 | 28 / 121 / 82 | 28 / 2 / 3 |
| 출퇴근 / 매출보고 / 지출 | 921 / 195 / 437 | 0 / 0 / 0 |
| Storage 버킷·파일 | 0 / 0 | 0 / 0 |
| Edge Function | 8개 | 7개(운영에만 `manee-debug-session-check`) |
| 적용된 마이그레이션 | — | 신규 직원 프로필·식자재 설정 SQL은 **미적용** |

- **첨부파일(영수증·정산 사진)은 Storage가 아니라 `public.sales_reports`의 jsonb 열(`settlement_photos`, `receipt_photos`, `note_photos`)에 들어 있고 약 64 MB(DB의 대부분)입니다.** 따라서 "업무 데이터 17개 테이블 CSV"에는 사진이 있으나 파일이 매우 크고, DB 전체를 덤프하는 방식이 필요합니다.
- 기존 17개 목록에는 **체크리스트·공지·예약·프랜차이즈·구독 등 22개 테이블**이 없었습니다(`pg_dump`는 public/private 전체를 포함하므로 자동 해결).
- 로그인 계정은 `auth.users`(비밀번호 해시 포함)에 있으며 `pg_dump`의 auth 계정 덤프에 포함됩니다. 세션·리프레시 토큰, Edge Function 소스·비밀값, 프로젝트/Auth 설정, API 키는 **덤프 대상이 아닙니다**.
- 앱이 CDN에서 불러오는 Supabase SDK는 `@supabase/supabase-js@2`(고정되지 않음)이며 **지금 CDN이 돌려주는 버전은 2.116.0**(검토 시험과 동일)입니다. 배포 전 `@2.116.0`으로 고정하는 것을 권장합니다(앱 한 줄 변경, 승인 필요).
- Netlify 사이트 `winners-staffapp`의 서버 함수 환경변수는 **모든 배포 컨텍스트(deploy-preview 포함)에 운영 URL·운영 service_role 키가 들어 있습니다.** 스테이징 배포의 함수는 빌드 시 환경 설정이 차단하도록 만들어져 있고 테스트가 있지만, 안전을 위해 스테이징 시험은 **운영 비밀값이 없는 별도 Netlify 사이트**에 올리는 것을 권장합니다.

## 2. 이번에 만든 준비물 (로컬, 승인 불필요했던 범위)

- `security/backup-run.mjs`: `backup`(pg_dump 데이터·계정·정의 + 전후 행 수·해시 + 매니페스트), `verify`(파일 해시 재확인), `rehearse`(격리된 로컬 PostgreSQL에 실제 복원 후 행 수·내용 해시 대조). 연결 문자열·행 내용은 출력하지 않습니다.
- 로컬 PostgreSQL 17.6 도구(임시 폴더): 합성 데이터로 **백업 → 복원 → 6개 테이블 행 수·해시 전부 일치**를 확인했습니다. 이 과정에서 실제 결함 2건을 찾아 고쳤습니다(`-n`과 `-t`를 함께 쓰면 교집합만 덤프되어 대부분 누락, `pg_restore`의 `-d` 누락).
- 건너뛰던 실제 PostgreSQL 시험 2건을 일회용 로컬 PostgreSQL 17.6(포트 5432, 임시 비밀번호)에서 실행: **2건 모두 통과**(동시 승인·매장 코드 경합). Supabase가 아닌 일반 PostgreSQL 엔진 시험입니다.

## 3. 적용 순서에 추가되는 항목 (기존 런북 §4 기준)

0. 독립 백업(스테이징 → 운영 순, 아래 §4). 스테이징은 변경 전 백업만 필요, 운영은 적용 직전 최신 백업이 필요.
1. (기존) 기준 배포·사전 점검·SQL·검증·Edge·앱.
2. **식자재 설정**: `food-ratio-threshold.sql`을 `new-staff-self-profile.sql` 뒤에 적용 → 확인(`stores.food_ratio_threshold` 컬럼, RPC 실행 권한, 구성원 읽기) → QA 매장에서만 저장·초기화 시험. 되돌릴 때는 `food-ratio-threshold-rollback.sql`(**RPC 권한만 회수, 컬럼·값 유지**). 컬럼 DROP은 별도 승인 없이 하지 않습니다.
3. 앱 배포 전 SDK 고정 여부 결정, 배포 후 실제 로드 버전은 브라우저에서 `window.supabase` 로드 URL(개발자도구 Network의 jsdelivr 응답 헤더 `x-jsd-version`)로 기록.

## 4. 독립 백업 실행 절차(자격 증명이 준비된 뒤)

1. `MANEE_DB_URL`(Supabase 대시보드 → Connect → **Session pooler** URI, 비밀번호 포함)을 PC의 환경변수로 받는다(대화·저장소·ZIP에 넣지 않음).
2. 스테이징: `backup` → `verify` → `rehearse`. 운영: 같은 순서(읽기 전용, 운영 쓰기 없음).
3. 결과는 파일명·크기·SHA-256·테이블별 행 수만 보고. 백업 폴더는 저장소 밖(`Desktop\manee-backups\`)이며 개인정보·계정 해시가 있어 외부에 올리지 않는다.
4. "복구 가능" 표기는 **rehearse 통과 후에만**, 그것도 "격리된 로컬 PostgreSQL에서 복원됨"까지입니다. Supabase 프로젝트로의 실제 복원은 새 빈 프로젝트에서 별도 승인 후 확인합니다.

## 5. 스테이징 시험 성공 기준 (요약, 상세는 런북 §9·§12)

- 로그인 유지·토큰 갱신: 유지 체크 시 앱을 닫았다 열어도 로그인 유지, 갱신 뒤에도 유지, 해제 시 새 탭은 로그인 화면. 계정 전환: B 로그인 시 A 탭이 로그인 화면으로.
- 신규 가입→요청→승인→급여 설정, 동시 승인(중복 crew 0건), 호환 Edge 426, 출퇴근·급여·매출 기존 흐름, 식자재 설정(사장님만 저장, 매니저·직원 거절, 롤백 후 값 유지).
- 모든 요청 호스트가 스테이징뿐(운영 요청 0건), 기존 28개 스테이징 매장 행 변경 0건(전후 digest 동일).

## 6. 갱신 — 백업 도구 완성, SDK 고정, 스테이징 준비 (같은 날 후반)

- **SDK 고정**: `index.html` 370행 `@supabase/supabase-js@2` → `@2.116.0`(변경 1줄). CDN의 고정 주소 파일은 설치된 2.116.0과 **바이트 동일**(SHA-256 `84ee9bf4…d5ff6`)임을 확인했고, `sdk-pin.test.mjs`가 고정과 설치 버전 일치를 검사합니다. 로그인·토큰 갱신·브라우저당 한 계정 시험(125건)이 그대로 통과했습니다. Edge Function은 이미 2.116.0을 import합니다. 엑셀 라이브러리(`xlsx-js-style`)는 고정되지 않았으나 이번 범위 밖입니다.
- **`backup-run.mjs` 개선**(가상 데이터 + 일회용 로컬 PostgreSQL 17.6으로 시험, `backup-run.test.mjs` 9건 통과):
  - 하나의 **스냅샷**에서 digest와 모든 덤프를 만들어, 운영이 계속 바뀌어도 복원 결과가 스냅샷 digest와 정확히 같아야 합니다. 스냅샷 이후 라이브 DB의 변화는 "drift"로 따로 표시(정상)하고, 파일 손상·누락은 verify/rehearse가 실패로 판정합니다.
  - **포함 범위 검증**: 덤프 대상(public·private 전체 + `auth.users`·`auth.identities`)이 실제 덤프 목록(`pg_restore -l`)에 모두 있는지 확인하고 없으면 실패. 제외 목록(auth 세션·토큰·감사 로그 등)은 이유와 함께 매니페스트에 기록.
  - **사진(jsonb·bytea) 열**을 열 단위로 해시해 복원 결과와 대조(가상 데이터에서 영수증·정산 사진 열 2개 일치).
  - **복원은 원본에 실행될 수 없음**: `rehearse`는 대상을 지정하는 인자가 없고, 자체 임시 로컬 서버(127.0.0.1)만 만들며 PG*/MANEE_* 환경변수를 지워 원본으로 향하는 연결을 차단(원본 주소가 도달 불가여도 통과하는 시험 포함).
  - **로그·오류에 접속 정보·개인정보 없음**: 연결 문자열은 PG* 환경변수로만 전달(명령줄에 없음), 오류 메시지에서 비밀번호·사용자·호스트·supabase 주소·행 데이터(COPY 실패 시 출력되는 행)를 제거. 잘못된 비밀번호·연결 거부·잘못된 URI 시험에서 유출 0건.
  - **접근 제한·암호화**: 저장소 안 경로 거부, Windows `icacls`로 현재 사용자만 접근, 공개키 봉인(`keygen`/`seal`/`unseal`, RSA-OAEP + AES-256-GCM, 변조 탐지). 개인키 보관은 운영 절차 §4-1.
  - 이 도구가 아직 **증명하지 않는 것**: Supabase 자체로의 복원, 봉인 개인키의 안전한 보관, 실제 운영 데이터에서의 소요 시간·크기(운영 사진 ≈64 MB).
- **스테이징 준비**: `scripts/staging-build.mjs`(운영 기준 `2e4e162`와 변경본을 각각 별도 폴더에 스테이징 컨텍스트로 빌드), `staging-preflight.mjs`(앱·함수 가드·운영 주소/키 부재·SDK 고정 점검), `netlify-env-check.mjs`(사이트·팀 변수에 운영 URL/키/시크릿이 있으면 중단, 값은 출력하지 않음), `staging-deploy.mjs`(운영 사이트 id·`--prod` 거부, 점검 통과 시에만 초안 배포 명령을 출력, `--execute` 없이는 실행하지 않음). 시험 8건(`staging-guards.test.mjs`).
- 시험표: `staging-qa-checklist.md`, 운영 적용·복구: `production-rollout-procedure.md`.

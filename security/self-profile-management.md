# 본인 관리 개인정보 (2026-09-20)

직원·매니저가 이름·연락처·은행·계좌번호·예금주를 본인이 관리하고, 연결된 승인 매장이 그 정보를 가져갑니다.

## 서버 (security/self-profile-management.sql, 추가 전용)
- `private.staff_self_profiles`: 본인 기본정보(모두 선택 입력) + 개정 번호. `private.profile_change_events`: 사장님 안내용(항목 이름·시각만, 값 없음). `private.profile_prior_values`: 매장 값이 본인 값으로 바뀌기 전의 원래 값(클라이언트 접근 불가, 복구용).
- RPC: `manee_my_profile_state(p_reveal)` (본인 멤버십으로 연결된 crew 행만; 기본은 계좌 마스킹, 수정 화면에서만 원본), `manee_save_my_profile(profile, expected_revision)` (본인만, 충돌은 SQLSTATE PT409 = HTTP 409; 40001은 게이트웨이가 재시도해 504가 되므로 사용 금지), `manee_owner_profile_changes(store_id)` (해당 매장 사장님만).
- 트리거 `manee_guard_self_managed_crew`: 본인 관리(self_service_profile=true) 직원의 이름·전화·계좌 문자열은 API(authenticated)로 매장이 바꿀 수 없음. 시급·근무조건·수습·입사일·공제·직급·권한·메모는 그대로 매장 관리. 플래그를 API로 되돌릴 수도 없음.
- 저장 시: 본인의 활성 멤버십 crew 행에만 반영, 비어 있는 항목은 매장 값을 지우지 않음. 승인(approve / approve_new) 시 본인 정보가 있으면 새 매장이 가져감(포털 래퍼 확장).
- 롤백(self-profile-management-rollback.sql): RPC 회수, 트리거 제거, 래퍼 원복. 표와 값은 삭제하지 않음.

## 화면
- 내 개인정보(조회, 계좌 마스킹, 미입력/조회 실패 구분) → 내 정보 수정(기존 매장 값 제안, 매장 간 충돌은 직접 선택, 나눌 수 없는 계좌 원문은 그대로 보여 주고 추측하지 않음) → 변경 내용·반영 매장 확인 → 저장 → 매장별 결과.
- 사장님 직원 관리: "직원이 직접 수정한 정보" 안내와 "본인 관리" 표시.

## v2 (검토 SP-01~06 보완, self-profile-management-v2.sql)
- SP-01: 기존 직원 행 연결 승인(approve)은 이름·연락처·계좌를 바꾸지 않음. 값이 다른 매장은 본인이 화면에서 차이를 확인하고 체크한 매장만 반영하며, 서버가 본인이 본 값(seen)과 현재 값이 같은지 다시 확인(다르면 409 store_values_changed). 빈 신규 행(approve_new)만 본인 정보로 초기화.
- SP-03: 은행·계좌·예금주는 하나의 묶음. 셋이 모두 있을 때만 매장의 계좌 문자열을 교체, 일부만 있으면 "보류"(held)로 알리고 기존 값 유지.
- SP-04: 기본 조회는 모든 계좌를 가림(5~7자리 전부, 8~11자리 뒤 3자리, 12자리 이상 앞 3·뒤 4). 분해할 수 없는 매장 문자열은 숫자를 전부 가림.
- SP-06: 은행 문자열은 " / "로 정확히 3부분이고 가운데가 숫자 형식일 때만 분해.
- 이전 앱(2개 인자 호출)도 그대로 호출되지만 서버가 같은 규칙을 적용(확인 없는 기존 값 교체 없음).
- 롤백은 기존 self-profile-management-rollback.sql(값·표 유지, 함수 권한 회수·트리거 제거·포털 원복). 이미 반영된 매장 값을 되돌리는 기능은 아님(원래 값은 private.profile_prior_values 에 보관).

## v3 (재검토 V2-01·V2-C1, self-profile-management-v3.sql)
- V2-01: "본인 관리"(self_service_profile) 표시가 "매장의 모든 기존 값을 이어받음"을 뜻하지 않도록, 이름·연락처·계좌 항목별 이어받기 기록(`private.profile_adoption`)을 추가. 매장의 기존 값은 (a) 이전에 이어받은 항목, (b) 매장 값이 비어 있음, (c) 본인이 본 값을 확인함(서버 재검사), (d) 승인으로 새로 만든 빈 직원 행 중 하나일 때만 바뀜. 빈 프로필·같은 값·일부 계좌만 저장해도 아무것도 이어받지 않음. 기존 두 인자 호출에도 동일 적용. 이미 표시가 켜져 있던 행은 세 항목을 이어받은 것으로 기록(표시가 뜻하던 바 그대로; 새 표에 INSERT만 하고 값은 바꾸지 않음).
- V2-C1: 저장과 신규 승인(approve_new)이 같은 사용자별 잠금(`pg_advisory_xact_lock`)을 잡아 직렬화. 승인은 잠금 획득 후 그 시점의 최신 프로필을 읽고, 이후 저장은 새 매장 행까지 반영. 서로 다른 행만 잡으므로 교착 없음(승인은 새 행만, 저장은 기존 행만 잠금).
- 상태 응답에 항목별 `adopted`, 확인이 필요한 항목 `pending` 추가(값은 포함하지 않음).
- 이어받기 기록의 일괄 보정은 표를 처음 만들 때 한 번만 실행합니다(V3-01). v3 파일을 다시 실행해도 기록을 추가하지 않아, 보류한 계좌가 이어받기 완료로 바뀌지 않습니다.
- 재가동(롤백 후): **v3 파일만** 실행한 뒤 verify. v3가 가드 트리거·권한·공개 함수·현재 포털 함수를 되돌립니다. v1을 다시 실행하면 남아 있는 3인자 저장 함수와 충돌(42725)하므로 금지. v1 → v2 → v3 순서는 이 객체들이 전혀 없는 새 설치에서만 씁니다(V3-03, 스테이징에서 롤백→v3→verify 전 과정 확인).

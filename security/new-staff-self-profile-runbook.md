## 원칙: 기존 데이터 보존 (모든 업데이트에 적용)

기존 출퇴근, 매출, 급여, 개인정보·계좌, 매장·직원 연결 기록을 업데이트 때문에 수정·삭제·초기화하거나 덮어쓰지 않습니다.

- 스키마 변경은 **추가만**(새 테이블·컬럼·함수). 기존 행·컬럼의 삭제, 타입 변경, 기본값으로의 덮어쓰기는 하지 않습니다.
- 기존 행을 바꾸는 SQL(`catchup.sql` 등)은 자동 적용·복구 절차에서 제외하고, 대상과 영향을 보고해 건별로 승인을 받습니다.
- 모든 변경은 "기존 데이터가 화면에서 정상 조회되고 기능이 유지되는지"로 확인합니다: 보존 함수 9개의 해시(매출보고 양식·제출, 급여 계산 2종, 직원 추가, 근무조건 등), 기존 테스트 전체, 조회 화면 확인, 확인 중 쓰기 요청이 0건인지.
- 시험은 별도 테스트 매장과 가상 직원으로만 하고 기존 행은 조회만 합니다.
- 적용 전에 독립 백업 상태를 사실대로 보고합니다(§3). 백업이 없으면 "없다"고 표시합니다.

## 2. 외부 서비스: 차단 확인 vs 실제 연동 검증

스테이징 빌드는 `netlify/functions/lib/manee-environment.json`의 `externalServicesEnabled=false`이고, 운영 빌드만 `true`입니다.
차단을 해제하거나 운영 키·실제 직원 알림으로 시험하지 않습니다.

| 기능 | 스테이징 동작 | 이미 확인한 것(코드/테스트) | 검증하지 않은 것 |
|---|---|---|---|
| 사진 **첨부**(영수증·특이사항·정산표) | 차단 없음. 브라우저에서 `data:` URL로 읽어 보고서 초안에 담음. Storage 업로드 코드는 없음 | 코드 경로 확인 | 실제 기기 사진 선택, 큰 사진의 저장 크기 |
| 사진 **분석**(정산표 자동입력) | `read-receipt` 함수가 503 `staging_external_service_disabled` | 차단 로직·503 응답을 `environment-isolation.test.mjs`가 검증(통과) | 실제 Anthropic API 호출·응답 해석·결과 채움 |
| 앱 도우미(`ask-app`) | 같은 방식으로 503 | 위와 동일 | 실제 API 호출 |
| 푸시 구독/발송 | 프런트가 `MANEE_IS_STAGING`이면 구독을 건너뜀, 서비스워커는 push 이벤트를 무시, `send-push`·예약 알림 cron은 503 | 테스트 통과 | 실제 푸시 전달, 실직원 알림 |

스테이징에서 확인 가능한 것은 "차단이 의도대로 동작하고 화면이 실패를 안내하는지"까지입니다. 실제 외부 연동은 운영 환경에서만 검증되며, 이번 변경이 그 코드를 수정하지 않았다는 점(`read-receipt`/`send-push` 무변경)으로 위험을 낮출 뿐입니다.
CLI로 만든 시험 배포는 사이트 환경변수가 함수에 주입될 수 있으므로, 배포 직후 `read-receipt`가 503을 돌려주는지 먼저 확인합니다(§11).

### 3.3 복구 방법과 "복구 가능"의 기준

**복구 방법(파일 → 복원)**
1. 임시 스키마(예: `manee_restore_check`, 스테이징) 또는 별도 프로젝트에 대상 테이블 구조를 `create table … (like public.<이름> including all)`로 만들고 CSV를 대시보드의 import(또는 `\copy`)로 적재합니다.
2. 같은 다이제스트 조회를 복원본에 실행해 행 수와 해시를 원본 기록과 비교합니다.
3. 핵심 조회를 재현합니다: 직원 목록·계좌 표시, 매출 합계, 급여 계산 결과가 원본과 같은지.
4. **실제 복구에서도 기존 행을 덮어쓰지 않습니다.** 없는 행만 `insert … on conflict do nothing`으로 채우고, 차이 나는 행은 목록으로 보고해 승인을 받은 뒤 처리합니다.

**판정 기준**: "내보내기 확보"는 "복구 가능"이 아닙니다. 복구 가능은 (a) §3.5의 내보내기 확인, (b) 위 복원 리허설 통과, (c) 복원 절차 승인이 **모두** 있을 때만 표시합니다. 현재 (a)(b)(c) 모두 수행되지 않았습니다.

### 3.4 값이 잘못 바뀐 사고 — "없는 행만 채우기"로는 복구되지 않습니다

`insert … on conflict do nothing`은 **없어진 행**만 채웁니다. 행은 남아 있는데 **값이 잘못 바뀐 사고**(급여·계좌·연락처가 다른 값으로 변경 등)는 복구하지 못합니다. 이 경우의 계획입니다. 자동으로 기존 행을 덮어쓰지 않습니다.

1. **현재 상태를 먼저 저장**합니다: 사고 시점의 현재 값을 같은 방식으로 내보냅니다(`after.csv`). 복원 뒤에 "사후 백업"으로도 씁니다.
2. **변경 전후를 대조**합니다: `node security\backup-tools.mjs diff before.csv after.csv --key id --out diff-report.txt`. 결과에는 **행의 키와 바뀐 컬럼 이름만** 나오고 값은 나오지 않습니다(추가·삭제·변경 행 구분).
3. **대상 확정과 별도 승인**: 보고서를 검토해 복원할 행과 컬럼을 지목하고, 그 지목을 명시한 승인을 받습니다. 백업 이후에 정당하게 바뀐 값은 되돌리면 함께 사라지므로 행마다 확인합니다.
4. **필요한 행·컬럼만** 복원합니다: 트랜잭션 안에서 `update … set <승인된 컬럼>=<백업 값> where <키>=…`를 실행하고, 영향 행 수가 승인된 수와 같을 때만 commit합니다. 다른 컬럼과 행은 건드리지 않습니다.
5. 복원 뒤 화면에서 해당 직원·급여·계좌가 정상 조회되는지 확인합니다.

한계: 백업 파일은 `NULL`과 빈 문자열을 구분하지 못합니다. 그런 칸은 컬럼 정의를 보고 원래 값을 정합니다. 복원 SQL은 값이 들어가므로 로컬 파일로만 다루고 대화에는 올리지 않습니다.

### 3.5 사용자가 직접 해야 하는 부분 — 독립 파일 백업 단계별 안내

로그인과 파일 저장은 사용자가 직접 합니다. 개인정보·비밀번호·CSV 내용·토큰은 대화에 붙여넣지 않습니다.

1. 브라우저에서 Supabase 대시보드(`supabase.com/dashboard`)에 **본인 계정으로 직접 로그인**합니다(비밀번호는 브라우저에만 입력).
2. 프로젝트 목록에서 **`manee-staging`**을 엽니다. 주소가 `…/project/obpkzecgswnfuyhwvncd`인지 확인하고, 운영 프로젝트 `staff`(`bhwuuxcrzxespkjlmqxr`)가 아닌지 프로젝트 이름과 주소로 확인합니다.
3. 왼쪽 메뉴에서 **SQL Editor**를 열고 새 쿼리를 만듭니다.
4. 저장소의 `security\new-staff-self-profile-backup-queries.sql`을 열어 **"0. Digest"** 쿼리(첫 번째 `select … union all …;`)를 복사해 붙여넣고 실행합니다. 결과를 CSV로 저장해 `digest.csv`로 보관합니다. 열 이름은 `t, n, h` 그대로여야 합니다.
5. 같은 파일의 **1~18번 `select`를 한 번에 하나씩** 붙여넣어 실행하고, 결과마다 CSV 다운로드로 저장합니다. 파일 이름은 digest의 `t` 값 그대로 `public.crew.csv`, `auth.users_identity_map.csv` 형식으로 합니다(화면 배치는 대시보드 버전에 따라 다를 수 있음). 결과가 0행인 테이블도 저장합니다.
6. **18개를 모두 내보낸 뒤 "0. Digest"를 한 번 더 실행**해 `digest-after.csv`로 저장합니다. 18개를 따로 실행하는 동안 데이터가 바뀔 수 있어서, 이 두 번째 digest로 "내보내는 동안 바뀌었는지"를 확인합니다.
7. 파일은 **저장소 밖의 본인만 접근하는 폴더**(예: `문서\MANEE_backup_2026-09-19_staging`)에 모읍니다. 클라우드 동기화 폴더는 피하고, 가능하면 암호화 저장(BitLocker 등)을 씁니다.
8. **첫 백업 목록 생성(딱 한 번)**: PowerShell에서 저장소 폴더로 이동해 `node security\backup-tools.mjs init "문서\MANEE_backup_2026-09-19_staging"`을 실행합니다.
   - 필수 18개 대상이 digest에 **정확히 한 번씩** 있는지(누락·중복·초과·빈 목록 거부), 모든 파일이 있는지, 데이터 행 수(CSV 파서로 셈, 메모 칸의 줄바꿈 포함)가 digest와 같은지, `digest-after.csv`가 있으면 내보내는 동안 DB가 바뀌지 않았는지 확인합니다.
   - 통과하면 `BACKUP_MANIFEST.json`(파일별 SHA-256이 담긴 **기준**)을 만듭니다. 문제가 있으면 기준을 만들지 않습니다. 기준이 이미 있으면 **거부**하며 덮어쓰지 않습니다.
9. **이후 무결성 확인(언제든)**: `node security\backup-tools.mjs verify "…"` — 파일이 **기준과 같은지**(SHA-256, 행 수, 목록)만 확인합니다. 기준은 수정하지 않고 실행할 때마다 **새 날짜 로그**를 남깁니다. 로그가 새로 생겼다는 사실은 파일이 그대로라는 증거가 아닙니다.
10. **(선택) DB가 백업 이후 바뀌었는지**: SQL Editor에서 digest를 다시 실행해 `digest-now.csv`로 저장하고 `node security\backup-tools.mjs db-check "…" "…\digest-now.csv"`를 실행합니다.
11. 저에게는 각 명령의 마지막 결과 줄만 알려 주세요("No problems found…" 또는 `PROBLEMS` 아래 목록). 파일 내용은 알려 주지 않아도 됩니다.

`node`가 없으면 각 CSV의 행 수를 `(Import-Csv .\public.crew.csv | Measure-Object).Count`로, 해시를 `Get-FileHash .\public.crew.csv`로 확인해 직접 기록합니다(기준 해시 보존과 자동 대조는 도구가 있을 때만 가능).

**각 확인이 증명하는 것과 증명하지 못하는 것**

| 확인 | 명령 | 증명하는 것 | 증명하지 못하는 것 |
|---|---|---|---|
| 내보내기 목록·행 수 | `init` | 필수 18개가 정확히 한 번씩 있고, 파일이 모두 있고, 행 수가 digest와 같음 | 파일 내용이 DB와 같다는 것 |
| 내보내는 동안 DB 불변 | `init`(`digest-after.csv`) | 18개를 내보내는 사이 digest가 같았음 | 완전한 단일 시점 스냅샷(각 쿼리는 서로 다른 시각에 실행됨). `digest-after.csv`가 없으면 "확인 안 함"으로 기록 |
| 파일 변경 여부 | `verify` | 파일이 **기준을 만든 시점 이후** 바뀌지 않았음(SHA-256) | 기준을 만들기 전에 이미 잘못된 파일 |
| DB 변경 여부 | `db-check` | 지금 DB의 digest가 백업 시점과 같음(또는 어느 테이블이 다름) | CSV 내용 = DB 내용(digest 해시는 DB 행 표현이라 CSV와 직접 비교할 수 없음) |
| CSV 내용 = DB 내용 | — | **확인하지 않음** | — |
| 복원 가능 여부 | 복원 리허설(§3.3) | **확인하지 않음**(수행하지 않음) | — |

### 3.6 기존 로그인 계정과 직원 연결까지 복구하는 방법

18개 내보내기는 **업무 데이터와 계정 식별 대응표**까지만 담습니다. 비밀번호 해시·토큰·Auth 설정이 없으므로 **로그인 계정 자체는 이것만으로 복구되지 않습니다.** 계정 복구는 아래 세 가지 중에서 고릅니다. **세 방법 모두 복원 리허설 전에는 검증되지 않았습니다.**

| 방법 | 복구되는 것 | 필요한 것 | 위험·한계 |
|---|---|---|---|
| **A. 유료 플랜의 DB 백업/PITR** | **데이터베이스 내용**(`auth` 스키마의 계정 데이터 포함)을 백업 시점으로 복구 | Supabase 유료 플랜. 공식 문서 기준 보관: Pro 7일·Team 14일·Enterprise 30일, **Free는 자동 백업 없음**. PITR은 Small 컴퓨트 애드온이 필요하고, 켜면 일일 백업 대신 쓰임 | **모든 것을 복구하지 않습니다.** **Storage API로 올린 실제 파일 객체는 DB 백업에 포함되지 않습니다**(DB에는 메타데이터만 있음, 공식 문서). Edge Function 소스·비밀값, 프로젝트·Auth 대시보드 설정, API 키는 공식 문서가 백업 범위로 **명시하지 않으므로 포함된다고 가정하지 않고 별도로 보관**합니다. 복구 시점은 백업 주기(일일) 또는 PITR 설정에 따릅니다. 법인 전환 후로 미룬 사항(현재 Free, 백업 없음) |
| **B. 개인 보관용 전체 덤프**(`auth` 스키마 포함, 비밀번호 해시 포함) | 계정과 비밀번호까지 그대로 | Supabase CLI(`supabase login`), DB 비밀번호, 보통 Docker. 사용자 PC에서 직접 | 파일에 **비밀번호 해시**가 들어 있어 유출 시 위험. **암호화 저장 필수**, 검토용 ZIP·저장소·대화 금지. Auth 스키마를 복원하는 절차는 위험하므로 리허설 필수 |
| **C. 해시 없이 계정 재생성**(대응표 사용) | 계정 식별(`user_id`)과 모든 연결. 비밀번호는 복구되지 않음 | `auth.users_identity_map.csv` + `profiles`, 관리자 권한 | 계정을 **같은 `user_id`로** 다시 만들 수 있는지(관리 API가 `id` 지정을 받는지)는 **확인하지 않았습니다.** 안 되면 새 `user_id`로 연결 테이블을 옮겨야 하며 별도 승인이 필요. 사용자는 기존 비밀번호 재설정 절차로 새 비밀번호를 만들어야 함 |

방법 A의 범위 참고: 이 앱의 코드에는 Storage 업로드가 없고 매출 사진은 DB에 `data:` URL로 저장됩니다(코드 조사 결과). 그래서 Storage 파일 손실 위험은 낮아 보이지만, 실제 프로젝트에 버킷이 있는지는 대시보드에서 확인하지 못했습니다. 유료 전환 여부와 무관하게 "DB 백업으로 복구되는 것 / 되지 않는 것 / 별도 보관할 것"을 이 표대로 구분해서 씁니다.

**계정 + 직원 연결 복구 순서**(방법 B 또는 C 이후)
1. `auth.users` 복원 또는 재생성(같은 `user_id`) → 2. `profiles` → 3. `stores` → 4. `store_memberships` → 5. `crew` → 6. `staff_link_requests`, `staff_access_events`, `store_staff_code_history` → 7. 출퇴근·매출·지출 등.
각 단계 뒤에 행 수와 키 존재를 확인합니다(기존 행은 덮어쓰지 않음). 마지막에 QA 계정으로 로그인해 사장님 홈의 매장 목록, 직원 연결, 급여·계좌 표시가 정상인지 확인합니다.

현황: 스테이징 계정은 3개입니다. **운영에는 훨씬 많은 실계정이 있으므로, 운영 반영 전에 방법 A 또는 B가 준비되어야 합니다.** 지금은 어느 것도 준비되지 않았습니다.

### 3.7 검토용 ZIP과 개인 보관 복구 백업은 다릅니다

| | 검토용 ZIP | 개인 보관 복구 백업 |
|---|---|---|
| 목적 | GPT의 코드·문서 검토 | 사고 시 데이터 복구 |
| 담는 것 | 코드, 패치, 테스트, 문서, 가상 데이터 스크린샷, 함수 정의 스냅샷 | 업무 데이터 CSV, 계정 식별 대응표, `digest.csv`, `BACKUP_MANIFEST.json`(기준 해시)와 확인 로그(+ 선택: 방법 B 전체 덤프) |
| 넣지 않는 것 | 실제 개인정보, 데이터 덤프·CSV, 비밀번호·해시, 키, 토큰, 접속 문자열 | 위 ZIP에 넣지 않는 모든 것은 **여기에만** 있음. 방법 B를 쓰지 않으면 해시·토큰도 없음 |
| 보관 | 검토자에게 전달 | 사용자 PC의 암호화된 폴더(저장소 밖) |
| 대화에서 | 파일 목록·해시 공유 가능 | 내용 출력 금지. 행 수 일치 여부만 |

이 구분 때문에 ZIP에서 비밀정보를 뺀다고 해서 복구용 백업에서도 빼야 하는 것은 아닙니다. 복구에 필요한 범위는 §3.2, §3.6에서 따로 정합니다.

### 3.8 예정: 동일 DB 안 복사본 (승인 후, 적용 직전, 스테이징만)

독립 백업이 아니며 프로젝트가 손상되면 함께 사라집니다. 원본과 같은지는 다이제스트 해시 비교로만 확인하고, 그 뒤에도 "복구 가능"으로 표시하지 않습니다.

```sql
create schema if not exists manee_backup_20260919;
revoke all on schema manee_backup_20260919 from public, anon, authenticated;
-- 업무 데이터 17개 테이블마다:
create table manee_backup_20260919.crew as select * from public.crew;
alter table manee_backup_20260919.crew enable row level security;
-- … stores, profiles, store_memberships, attendance, sales_reports 등 같은 방식
```

## 4. 스테이징 적용 순서 (보류 중)

각 단계 뒤에 검증하고, 실패하면 다음 단계로 가지 않습니다. 사용자 승인 후 진행합니다.

0. **기준 배포 만들기**(§11): 되돌릴 스테이징 배포가 현재 없으므로 `2e4e162` 기준 배포를 먼저 만들어 주소를 기록.
1. **사전 점검**: `verify.sql`을 phase `'preflight'`로 실행 → `problems = 0`. 기준 해시가 다르면 중단하고 다시 검토.
2. **독립 백업(내보내기)**: §3.5 절차로 파일을 확보하고 `backup-tools.mjs init`(첫 백업 기준 생성)으로 목록·행 수를 확인한 뒤 이후 `verify`로 기준 대비 변경 여부를 확인(권장 게이트). 이것은 **부분 데이터 백업**이며 로그인 계정 자체는 포함하지 않고(§3.6), "복구 가능"이라고 표시하지 않습니다(§3.3). 이어서 동일 DB 복사본(§3.8, 독립 백업 아님).
3. **DB**: `security/new-staff-self-profile.sql` 실행.
4. **DB 검증**: `verify.sql`을 phase `'applied'`로 실행 → `problems = 0`.
5. **Edge Function**: 스테이징 `manee-staff-signup`에 새 `index.ts` 배포. **DB보다 먼저 배포하면** 새 앱의 가입이 RPC 부재로 실패합니다.
6. **앱**: 스테이징 시험 배포(§11). 빌드 후 `netlify/functions/lib/manee-environment.json` 변경 여부를 확인하고 커밋하지 않습니다(`dist/`·`node_modules/`도 제외).
7. §9 시나리오 실행.

## 5. 복구 순서 (자동 복구 절차)

**Edge를 가장 먼저** 되돌립니다. 이미 열려 있는 새 앱 탭은 프런트를 되돌려도 계속 남아 구 Edge를 호출할 수 있기 때문에, "프런트 배포 순서"만으로는 조용한 유실이 막히지 않습니다. 호환 Edge의 가드가 그 창을 즉시 닫습니다.

1. **Edge Function(호환본)**: `security/edge-rollback/manee-staff-signup-v1-compat.ts`를 slug `manee-staff-signup`, `verify_jwt=false`로 배포. 원본 v1을 그대로 다시 올리지 않습니다(그러면 새 앱의 `personal`이 조용히 버려짐).
   - 동작: 본문에 `personal`이 있으면 계정·속도 제한 소모 전에 HTTP 426 `app_update_required`("앱이 업데이트되어 가입 정보를 저장할 수 없어요. 화면을 새로고침한 뒤 다시 가입해 주세요. (입력하신 정보는 저장되지 않았어요)")를 반환. 프런트는 한글 `message`를 토스트로 표시함(`callManeeAuthApi` → `staffErrorMessage`, 별도 매핑이 없는 코드는 한글 메시지를 그대로 사용). 토스트는 잠깐만 보이므로 테스트 때 문구가 실제로 보이는지 확인할 것.
   - 그 외 요청은 원본 v1과 동일(원본 v1에 가드 블록 하나만 추가된 것을 해시로 검증).
2. **배포 확인(부작용 없음)**: 공개키로 `POST {"personal":{}}` → **426 `app_update_required`**여야 함. 400 `invalid_username`이면 호환본이 아닌 것. 이 요청은 계정을 만들지 않고 속도 제한도 쓰지 않습니다.
3. **프런트**: 기준 배포 주소로 되돌림(§11). 서비스워커는 캐시를 하지 않으므로 새로고침하면 바로 반영됩니다.
4. **DB**: `new-staff-self-profile-rollback.sql` 실행 → `verify.sql` phase `'rolled_back'`로 확인.
5. 롤백 SQL이 "`before_self_profile` 없음/래퍼가 아님"으로 중단되면 아무것도 바꾸지 않은 상태입니다. 그때만 함수 정의 스냅샷 파일로 포털을 복원합니다.

**`catchup.sql`은 이 자동 절차에서 실행하지 않습니다.** 롤백 기간에 승인된 신규 직원이 생겼다면 별도 절차로 다룹니다: (1) 미리보기만 실행해 대상 crew id·매장·급여·설정 대기 여부(개인정보 제외)를 보고 → (2) 바뀌는 행과 항목을 명시 → (3) 그 행을 지목한 승인이 있을 때만 확인 값을 설정해 실행. 기존 직원 정보 변경이 필요한 경우도 같은 방식으로 대상과 영향을 보고하고 승인을 받습니다.

**남기는 것(삭제하지 않음)**: `private.staff_registration_profiles` 테이블과 행, `crew` 컬럼 2개, `bootstrap_staff_account_with_profile`, 이미 만들어진 가입 계정·직원 연결·crew 행.

### 9.1 실제 동시 승인 검증 — 두 가지 경로

기존 `store-code-concurrency.test.mjs`와 새 `new-staff-self-profile-concurrency.test.mjs`는 **로컬/CI 전용**입니다. 접속 주소가 `postgres@127.0.0.1|localhost:5432/manee_code_test` 형식이 아니면 실패하도록 고정돼 있고, 스테이징 DB에 연결하지 않고, 연결해서도 안 됩니다.

1. **일회용 PostgreSQL 17(CI 또는 로컬)** — 8개 동시 `approve_new`로 crew 1행, `created_new` 1건, 급여 재설정 없음을 검증. 이 PC에는 `psql`·`docker`가 없어 아직 실행하지 못했고, CI 실행은 push가 필요합니다.
2. **스테이징 가상 계정 프로브** — `security/staging-concurrency-probe.mjs`(수동 실행 전용)
   - 스테이징 앱 API(공개키 + QA 계정 자신의 세션)만 사용. 서비스 키·SQL·삭제 없음.
   - 거부 조건(로컬에서 확인함): URL이 스테이징과 정확히 일치하지 않음, 운영 URL, 운영 공개키, QA 접두사가 없는 계정명, 시험 매장 아님(사장님 세션의 소속 매장 이름이 `[QA-0919]`로 시작하지 않음). `--dry-run`은 네트워크 요청 없이 설정만 검증.
   - `--phase=approve`: 직원이 6개 동시 요청 → 사장님이 8개 동시 `approve_new` → 요청 1건·crew 1행·플래그 확인. 사장님이 앱에서 급여를 저장한 뒤 `--phase=retry`: 4개 동시 재승인 → 기존 기록 반환·급여 유지.
   - 필요: 스테이징에 만든 QA 사장님·직원 계정과 시험 매장(매장 id·8자리 코드), 계정 비밀번호(환경변수로만 전달, 출력·저장 안 함).
   - 한계: 한 사장님의 동시 호출만 검증. 서로 다른 두 사장님의 동시 승인은 시험 매장에 사장님이 한 명뿐이라 다루지 못함. 스테이징에서 사장님 계정 생성이 별도 승인 절차를 요구하는지는 확인하지 못했습니다.
   - 두 경로는 서로 대체하지 않습니다. 프로브는 배포된 실제 Supabase 경로를, 로컬/CI는 스키마 전체를 새로 만든 DB를 검증합니다.

## 10. 남은 장애물

1. **실제 PostgreSQL 동시성 테스트를 실행할 환경이 없습니다.** `psql`·`docker`가 없고, CI 실행은 push가 필요합니다. 스테이징 프로브는 QA 계정 준비(스테이징 적용·앱 배포 이후)가 필요합니다.
2. **Supabase에서의 실제 실행**(새 SQL, 권한, PostgREST, 배포된 Edge 호출)은 스테이징 적용 전까지 미검증입니다. 호환 Edge의 426 응답도 실제 배포 후에 확인됩니다(로컬 하네스에서는 통과).
3. **실제 데이터의 독립 백업이 없습니다.** §3.5는 사용자의 대시보드 접근이 필요하며, 내보내기는 **부분 데이터 백업**이라 로그인 계정 자체는 복구하지 못합니다(§3.6). 내보내기를 마쳐도 복원 리허설 전에는 "복구 가능"으로 표시하지 않습니다.
4. **되돌릴 스테이징 배포가 없습니다**(§11). 적용 전에 기준 배포를 만들어야 합니다.
5. 본사·프랜차이즈 스테이징 계정 존재 여부를 확인하지 못했습니다.
6. **스테이징에는 출퇴근·매출·지출·급여 조정 실데이터가 없습니다**(§3.1). 이 영역의 보존 검증은 가상 데이터와 자동 테스트, 시험 매장에서 새로 만든 기록으로만 가능합니다.
7. 가입 후 직원 본인 정보 수정은 이번 범위가 아닙니다. 후속 설계는 "직원 저장 → 연결된 매장에 반영 → 사장님에게 변경 알림"이며 사장님 승인을 기다리지 않습니다. 이번 SQL·앱에는 넣지 않았습니다.

## 12. 실제 스테이징에서 확인할 미검증 항목

아래는 로컬 검증으로는 확인할 수 없거나 확인하지 않았고, 실제 스테이징(§4 순서로 적용·배포 후)에서 확인합니다.

**서버·배포 측**
- **호환 Edge의 426 응답**: 배포 후 `POST {"personal":{}}` → 426 `app_update_required`.
- **이미 열린 새 앱에서의 오류 안내**: 롤백 뒤에도 남아 있는 새 앱 탭이 가입을 시도할 때 "화면을 새로고침한 뒤 다시 가입해 주세요" 문구가 토스트로 실제 보이는지(토스트는 잠깐만 표시).
- **동시 승인**: `staging-concurrency-probe.mjs`(스테이징)와 일회용 PostgreSQL(CI)에서.
- **기존 기능 보존**: 출퇴근, 매출 저장·사진 첨부, 급여 계산, 직원 추가·수정, 엑셀 내보내기. 스테이징에 실데이터가 없으므로 시험 매장에서 새로 만든 기록으로 확인.
- 외부 서비스는 차단 동작(503)만 확인하고 실제 연동은 검증하지 않음(§2).

**이번 UI·세션 변경(로그인 화면, 사장님 홈 상태, 로그인 상태 유지) — 로컬 가상 백엔드에서만 확인함**
- **로그인 유지와 토큰 갱신(실제 Supabase Auth)**: 실제 `manee-login` 응답과 실제 토큰 자동 갱신(기본 만료 약 1시간 뒤)에서, 체크·해제 각각 저장 위치가 바뀌지 않는지(DevTools Application → Storage). 가상 백엔드에서는 만료를 95초로 줄여 갱신 2회를 확인했고, 실제 만료 시간·실제 갱신 실패 처리는 미확인.
- **여러 탭의 계정 전환·로그아웃(실제 환경)**: 로컬에서는 "한 탭 로그아웃 → 다른 탭 로그인 화면", "오래된 로그인 화면에서 다른 계정 로그인 → 기존 탭이 새 계정으로 새로고침", "해제 탭은 다른 탭의 로그인·로그아웃에 영향받지 않음"을 확인. 실제 브라우저 종류별 차이는 미확인.
- **설치형 앱(PWA)·브라우저 재실행**: 새로고침·새 탭·새 브라우저 컨텍스트로만 시험했고 실제 앱 종료·재실행은 시험하지 못함. 일부 브라우저는 종료한 탭을 복원하면서 세션 저장소를 되살릴 수 있어서 **"해제하면 종료 시 반드시 로그아웃"이라고 보장하지 않음**. 확인된 동작만 설명함(체크 해제 세션은 탭·브라우저를 닫으면 사라지는 것이 기본이며, 복원 기능은 예외가 될 수 있음).
- **신규 가입 → 연결 요청 → 승인 → 급여 설정**: 스테이징 적용 후 시험 매장·가상 계정으로.
- **동시 승인**: 스테이징 프로브와 일회용 PostgreSQL(CI).
- **호환 Edge 426, 이미 열린 새 앱의 오류 안내**: 위와 같음.
- **기존 출퇴근·급여·매출보고 기능 보존**: 시험 매장에서 새로 만든 기록으로(스테이징에는 실데이터 없음).
- 실데이터로 본 사장님 홈의 상태 표시(안정·관리 필요·집계 전·매출 없음)와 기존 판정 기준의 일치.
- 실제 직원·매니저 계정 로그인 후 화면과 권한(이번 변경은 로그인 화면·저장소만 바꾸고 로그인 이후 화면 코드는 그대로), 본사·프랜차이즈 화면.
- 다크 모드 실기기 표시.

**GPT v2 검토에서 지적되어 로컬에서 고친 항목 — 실제 환경 확인은 아직 없음**

# 스테이징 실환경 시험표 (QA 매장 · 가상 계정 전용)

**상태: 전부 미실행입니다.** 이 표는 실행 전 준비이며, 실행 상태 열은 실제로 실행한 뒤에만 바꿉니다. 승인 전에는 스테이징 변경·배포를 하지 않습니다.

## 0. 시작 조건 (모두 충족해야 1번부터 시작)

| # | 조건 | 확인 방법 | 상태 |
|---|---|---|---|
| G1 | 스테이징 변경 전 독립 백업 확보(`backup-run.mjs backup → verify → rehearse → seal`) | 매니페스트·복원 예행연습 통과 출력 | **미확보** |
| G2 | 시험 배포 사이트가 운영과 분리되고 운영 비밀값이 없음 | `node scripts/netlify-env-check.mjs --site <시험 사이트 id>` → OK | 미실행(사이트 미생성) |
| G3 | 빌드 폴더가 스테이징만 가리킴 | `node scripts/staging-preflight.mjs <폴더>` → PASSED (변경본은 로컬 통과, 기준본은 `--baseline`) | 로컬 통과 |
| G4 | 배포 직후 `/app-config.js`가 스테이징, 개발자도구 Network에 운영 호스트 요청 0건 | 브라우저 확인 | 미실행 |
| G5 | 기존 스테이징 매장 기준선 기록(아래 §A) | 읽기 전용 SQL | 미실행 |
| G6 | 로드되는 SDK 버전 기록 | Network의 supabase.js 응답 헤더 `x-jsd-version` = 2.116.0 | 미실행 |

**§A 기존 매장 불변 확인용 기준선(읽기 전용, QA 매장 제외):** 시험 전후로 같은 값이어야 합니다. 식자재 컬럼 추가로 행 전체 해시는 달라지므로 컬럼을 지정합니다.
`select count(*), md5(string_agg((id,name,lat,lng,onboarding_done,manager_dashboard_enabled,business_day_cutoff_hour,archived_at)::text,'|' order by id)) from public.stores where id <> '<QA 매장 id>';` 및 같은 방식의 `crew`, `store_memberships` (QA 매장·가상 계정 행 제외).

## 1. 시험 절차와 성공 기준

| # | 시험 | 방법 | 기대 결과 | 실행 |
|---|---|---|---|---|
| T1 | 사장님·매니저·직원 로그인 | QA 매장의 가상 계정 3종으로 각각 로그인 | 각 역할 화면(사장님 홈 / 매니저 홈 / 직원 홈)이 열리고 다른 매장 데이터가 보이지 않음 | 미실행 |
| T2 | 로그인 상태 유지 | 유지 체크 로그인 → 브라우저·앱을 완전히 닫았다 열기 / 해제 로그인 → 새 탭 열기 | 체크: 다시 열어도 로그인 유지. 해제: 새 탭·재실행은 로그인 화면(**"종료 시 반드시 로그아웃"을 보장한다고 쓰지 않음**) | 미실행 |
| T3 | 토큰 갱신 | 로그인 후 만료 임박까지 사용(또는 1시간 이상 방치 후 조회) | 갱신 뒤에도 같은 계정 유지, 조회 성공, 오류 토스트 없음 | 미실행 |
| T4 | 계정 전환·브라우저당 한 계정 | 탭 A(사장님) 로그인 → 같은 브라우저 탭 B에서 다른 계정 로그인 / 틀린 비밀번호 시도 | B 성공 시 A 탭이 로그인 화면+안내로 이동, A 데이터가 B 화면에 없음. 틀린 비밀번호는 A에 영향 없음. **다른 기기의 로그인은 유지** | 미실행 |
| T5 | 로그아웃 | 각 탭에서 "다른 사용자로 전환" | 세션·마지막 매장 ID 정리, 다른 계정·기기 영향 없음, 이전 화면 데이터 잔존 없음 | 미실행 |
| T6 | 신규 가입→연결 요청→승인→급여 설정 | 직원 가상 계정 가입(개인정보·계좌 가상값) → 매장 코드로 요청 → 사장님 승인 → 급여 조건 설정 | 요청·승인 후 직원 기록 1건 생성, 개인정보 1회 복사, 급여 설정 반영, 기존 직원 행 불변 | 미실행 |
| T7 | 동시 승인 | 승인 화면 2곳에서 같은 요청을 동시에 승인 | crew 행 중복 0건, 두 번째는 정상 거절 메시지. (스크립트: `security/staging-concurrency-probe.mjs`, 승인 후 실행) | 미실행 |
| T8 | 호환 Edge 426 | 호환 Edge 배포 후 `POST {"personal":{}}` → 426 `app_update_required`, 이미 열려 있는 새 앱에서 가입 시 안내 문구 | 계정·속도 제한 소모 없이 426, 화면에 "새로고침 후 다시 가입" 안내 | 미실행 |
| T9 | 출퇴근 | QA 직원 계정으로 매장 100m 안에서 출근/퇴근 | 서버 시각으로 기록, 사장님 화면에 표시, 다른 매장 기록 불변 | 미실행 |
| T10 | 급여 | QA 매장의 급여 화면 | 시급·근무시간 계산이 시험 전과 같은 방식(수치는 가상 데이터의 기대값과 일치) | 미실행 |
| T11 | 매출·지출 저장과 조회 | 매출보고·지출 입력 후 조회·수정·삭제(QA 매장만) | 저장 후 홈·월간 리포트 금액 반영, 조회 실패 시 "—/조회 실패" 표시 | 미실행 |
| T12 | 엑셀 내보내기 | 스텝 전체·월간 리포트 엑셀 내보내기 | 파일 생성, 시트에 QA 데이터만, 열림 확인(엑셀 라이브러리는 CDN에서 로드) | 미실행 |
| T13 | 식자재 기준 설정 | 사장님: 더보기→매장 설정→식자재비율 경고 기준 저장(예 38%)·기본값으로. 매니저·직원으로 저장 시도 | 사장님만 저장, 저장 후 홈·월간 리포트·매니저 홈이 같은 기준·문구("식자재비율 38% 초과"). 인건비 22%. 권한 없는 계정은 거절. 기준 조회 실패 재현 시 "기준 조회 실패·판정 불가" | 미실행 |
| T14 | 비파괴 롤백(식자재 SQL) | `food-ratio-threshold-rollback.sql` 실행 → 값 조회 → 저장 시도 → 재적용 | 저장값 유지, 롤백 중 사장님도 저장 불가, 재적용 후 저장 가능, 다른 매장 값 불변 | 미실행 |
| T15 | 신규 직원 프로필 SQL 롤백 | 런북 §5 순서(호환 Edge → 앱 → `new-staff-self-profile-rollback.sql`) | 기존 계정·직원 연결·crew 행 유지, 지정된 보존 항목 남음 | 미실행 |
| T16 | 모바일 브라우저 | 휴대폰 브라우저에서 T1~T5, T9, T11, T13 | 화면 깨짐 없음(320~430px), 동작 동일 | 미실행 |
| T17 | 설치형 앱 재실행 | 스테이징 사이트를 홈 화면에 추가 → 로그인(유지 체크) → 앱 종료·재실행 → 유지 해제로 반복 | 체크: 로그인 유지. 해제: 재실행 시 로그인 화면 여부를 **관찰해 기록**(OS별 복원 동작 차이). 앱 이름 "매니 테스트" | 미실행 |
| T18 | 서버 함수 차단 | `ask-app`, `read-receipt`, `send-push`, 두 cron 함수 호출 | 모두 HTTP 503 `staging_external_service_disabled` | 미실행 |
| T19 | 기존 매장 불변 | 시험 후 §A 쿼리 재실행 | 시험 전 기준선과 동일(변경 0건), 운영 요청 0건 | 미실행 |

## 2. 이미 별도로 통과한 시험 (실환경 시험을 대체하지 않음)

| 시험 | 결과 | 범위 |
|---|---|---|
| 실제 PostgreSQL 동시 승인(`new-staff-self-profile-concurrency.test.mjs`) | **통과** | 일회용 로컬 PostgreSQL 17.6(Supabase 아님)에서 경합 승인이 crew 1행·프로필 1회 복사·급여 유지 |
| 실제 PostgreSQL 매장 코드 경합(`store-code-concurrency.test.mjs`) | **통과** | 같은 환경 |
| 재실행 방법 | `PGBIN=<PostgreSQL 17 bin>`, 포트 5432에 임시 비밀번호 클러스터 + `MANEE_TEST_DATABASE_URL=postgresql://postgres:<임시>@127.0.0.1:5432/manee_code_test` | Supabase에는 연결하지 않음 |
| 앱 자동 시험 | 383 + 새 시험(SDK 고정·백업 도구·스테이징 가드) | 가상 응답·PGlite·로컬 PostgreSQL |

T7은 로컬 결과가 있어도 **실제 Supabase(RLS·Edge 포함)에서 다시 확인**해야 합니다.

## 3. 시험 데이터 원칙

- QA 매장 1곳과 가상 계정(사장님·매니저·직원)만 만들고 사용합니다. 기존 28개 스테이징 매장·직원·계정은 조회 외에 어떤 변경도 하지 않습니다(§A로 확인).
- 시험 뒤에도 QA 데이터는 삭제·초기화하지 않고 표시만 남깁니다(별도 승인 없이 정리하지 않음).
- 개인정보·계좌는 가상 값만 씁니다. 스크린샷·기록에 실제 값이 없어야 합니다.

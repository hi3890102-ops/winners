## 2. 기존 데이터 보존 (앞으로 모든 업데이트에 적용하는 원칙)

기존 출퇴근, 매출·지출, 급여, 개인정보·계좌, 매장·직원 연결 기록을 업데이트 때문에 수정·삭제·초기화하거나 덮어쓰지 않습니다. 남아 있는 것뿐 아니라 **기존 화면에서 정상 조회되고 기능이 유지되는지** 확인합니다.

이번 변경의 영향과 확인:
- 서버로 나가는 요청은 **읽기뿐**입니다. 로그인, 홈, 직원관리, 급여, 매출 화면과 다중 탭·토큰 갱신 시나리오 전체에서 가상 백엔드가 받은 **쓰기(POST/PATCH/DELETE) 요청은 0건**이었습니다.
- 기존 직원의 이름·시급·전화·계좌가 표시되고 입력란은 수정 가능한 상태 그대로입니다. 급여 계산은 기대값과 일치했습니다(시급 10,000원 × 40시간 = 400,000원).
- 보존 함수 9개(매출보고 양식·제출, 급여 계산 2종, 직원 추가, 근무조건 등)의 해시가 main 원본과 같습니다(자동 테스트 통과).
- **한계**: 스테이징에는 출퇴근·매출·지출·급여 조정 실데이터가 0건이라 이 영역은 가상 데이터로만 확인했습니다.

## 3. 로그인 상태 유지 — 실제 세션 저장 방식과 연결

이전에는 체크 표시가 **화면 장식뿐**이었습니다(직원 인증이 꺼진 구식 로그인 경로에서만 쓰였고, 지금은 항상 Supabase 기본 저장소인 `localStorage`에 남았습니다). 실제 저장 위치와 연결했습니다.

### 3.1 동작 (확인된 것만)

| | ☑ 체크(기본) | ☐ 해제 |
|---|---|---|
| 세션(로그인 토큰) 저장 위치 | `localStorage` | `sessionStorage` |
| **마지막 선택 매장 ID** | 같은 선택을 따름(`localStorage`) | 같은 선택을 따름(`sessionStorage`) |
| 새로고침 | 로그인 유지 | 로그인 유지(같은 탭) |
| 새 탭·브라우저 재접속 | 로그인 유지 | 다시 로그인 필요(새 탭은 세션 저장소가 비어 있음) |
| 토큰 자동 갱신 | 갱신 뒤에도 `localStorage` | 갱신 뒤에도 `sessionStorage`(새로고침 뒤에도) |
| 로그아웃 | 세션·매장 ID 삭제 | 세션·매장 ID 삭제 |
| 비밀번호 | 저장하지 않음 | 저장하지 않음 |

- 기본은 체크 상태이고, 마지막 선택을 기억해 다음 방문 때 반영합니다. 저장되는 설정값은 `"1"`/`"0"` 하나뿐이며 비밀번호는 브라우저 저장소 어디에도 없습니다(저장소 전체 검사로 확인).
- 사장님 탭과 직원·매니저 탭이 같은 체크박스와 같은 로그인 처리를 씁니다. 회원가입 직후 자동 로그인은 체크박스가 없으므로 저장된 선택을 따릅니다.

### 3.2 안전 장치 (이번 보완)
- **업데이트만으로 강제 로그아웃되지 않습니다.** 저장 키를 바꾸지 않았고 읽을 때 두 저장소를 모두 봅니다. 유지 선택값이 없던 시절과 같은 상태(세션이 `localStorage`에만 있음)로 만들어 새로고침해도 로그인이 유지되는 것을 확인했습니다.
- **예전 세션이 되살아나지 않습니다(같은 계정의 중복만 정리).** 명시적인 로그인이나 로그아웃 때만, 반대 저장소가 **비어 있거나 같은 계정의 사본**이면 정리합니다. 같은 계정이 유지를 해제하고 다시 로그인하면 `localStorage`의 이전 사본이 지워져 닫았다 열어도 되살아나지 않습니다. **다른 계정의 세션은 이 탭이 지우지 않습니다**(§9 R2). 토큰 갱신은 반대 저장소를 건드리지 않습니다.
- **다른 계정의 세션이 선택되지 않습니다.** 읽을 때는 이 탭 자신의 `sessionStorage`를 먼저 봅니다. 그리고 **각 탭이 자기 로그인의 저장 위치를 기억**해서, 다른 탭이 공유 선택값을 바꿔도 이 탭의 토큰 갱신이 세션을 옮기거나 지우지 않습니다.
- 로그아웃은 **앱의 세션·매장 선택값만** 정리합니다. 저장소 전체 초기화(`clear()`)는 쓰지 않으며 다른 앱 데이터는 남습니다(테스트로 확인).
- 브라우저 저장소가 막혀 있으면 세션은 메모리에만 두고 저장하지 않습니다.

### 3.3 여러 탭 (가상 백엔드 브라우저에서 확인)
| 시나리오 | 결과 |
|---|---|
| 두 탭 모두 "유지" 로그인 상태에서 탭 2가 로그아웃 | 탭 1이 로그인 화면으로 이동하고 "다른 화면에서 로그아웃되어 …" 안내 |
| 탭 2가 오래된 로그인 화면에서 **다른 계정**으로 로그인 | 탭 1이 새로고침되어 새 계정의 데이터만 표시(이전 계정 데이터 없음) |
| 탭 1은 "해제", 탭 2는 "유지"로 다른 계정 로그인 | **(v5, 대표 결정) 브라우저당 한 계정**: 탭 2 로그인이 성공하면 탭 1은 자기 세션·화면 데이터를 정리하고 로그인 화면으로 이동("다른 계정으로 로그인해서 이 화면은 로그아웃됐어요"). 탭 2 계정만 남음 |
| 탭 1은 "유지" 로그인 중, 탭 2가 오래된 로그인 화면에서 **"해제"로** 다른 계정 로그인 | 위와 같음(반대 순서): 탭 1의 유지 로그인은 삭제되고 탭 1은 로그인 화면으로 이동. 탭 2(해제)의 세션은 탭 2에만 있고 `localStorage`에 복사되지 않음 |
| 탭 2에서 다른 계정 로그인이 **실패**(비밀번호 오류) | 탭 1은 아무 영향 없음(세션·표시·토큰 갱신 그대로) |
| **같은 탭**에서 로그아웃 후 다른 계정 로그인 | 새 계정의 홈으로 들어가고 이전 계정의 매장·집계가 보이지 않음(아래 3.4) |

동기화는 다른 탭의 이벤트를 믿지 않고 **이 탭이 실제로 가진 세션을 다시 읽어서** 판단합니다(다른 탭 이벤트, 저장소 변경, 탭이 다시 보일 때). 그래서 해제 탭은 다른 탭의 이벤트로 로그아웃되지 않습니다.

### 3.4 함께 발견·수정한 기존 문제: 계정 간 데이터 노출
수정 전 현재 코드에서 재현했습니다. **같은 탭에서 사장님 1이 로그아웃하고 사장님 2가 로그인하면, 사장님 2의 홈에 사장님 1의 6개 매장과 합산 매출 4,000,000원이 표시**됐습니다(홈 집계 캐시가 로그아웃 때 비워지지 않았고, 마지막 화면도 남았습니다). 이번 작업 이전부터 있던 문제입니다. 로그아웃(`clearStaffAuthView`) 때 집계 캐시·펼침 상태·열린 입력 화면·마지막 화면을 비우도록 고쳤고, 수정 후 사장님 2에게는 자기 매장만 보이고 홈으로 들어오는 것을 확인했습니다.

### 3.5 토큰 자동 갱신
가상 백엔드에서 만료를 95초로 줄여 실제 자동 갱신을 발생시켰습니다. 체크 상태에서 갱신 2회(두 번째는 다른 탭이 공유 선택값을 `0`으로 바꾼 뒤) 모두 저장 위치가 `localStorage`로 유지되었고, 해제 상태에서는 갱신과 새로고침 뒤에도 `sessionStorage`에 유지되었습니다. **실제 Supabase Auth의 실제 만료 시간·갱신 실패 처리는 미확인**입니다.

### 3.6 확인된 동작과 한계 — 보장하지 않는 것
- **"해제하면 종료 시 반드시 로그아웃된다"고 보장하지 않습니다.** 확인된 것은: 해제한 로그인은 `sessionStorage`에만 있어서 **새 탭·새 브라우저 컨텍스트에서는 로그인 화면이 나온다**는 것입니다. 일부 브라우저는 종료한 탭을 복원(예: "닫은 탭 다시 열기", 앱 복원)하면서 `sessionStorage`를 되살릴 수 있어, 그 경우 해제 상태에서도 로그인이 남을 수 있습니다.
- 설치형 앱(PWA)·실제 브라우저 재실행은 시험하지 못했습니다(미검증).
- 서버 쪽 세션 유효 기간은 Supabase 설정에 따르며 바꾸지 않았습니다.
- 다른 탭에서 **같은 계정**이 로그아웃하면 이 탭도 로그인 화면으로 이동합니다. 밀려난(다른 계정이 로그인한) 탭이 나중에 로그아웃하거나 토큰 갱신을 시도해도 새 계정의 세션·매장 ID·표식을 지우거나 덮어쓰지 않으며, 밀려난 탭은 되살아나지 않습니다(숨겨졌다가 다시 열려도 자기 세션은 버려지고 로그인 화면).
- 공용 기기에서는 체크를 해제하고 사용 후 로그아웃하는 것이 안전합니다.

### 3.7 테스트 계약 변경(의도적)
기존 테스트는 "운영은 SDK 기본 저장소를 그대로 쓴다(`createClient` 옵션 없음)"를 요구했습니다. 저장소 어댑터를 넣으면서 이를 **"어댑터만 추가하고 저장 키는 기본값 유지, 스테이징 키 이름은 그대로"**로 바꿨습니다. 저장 키가 같아야 기존 로그인 세션이 유지되므로 이것이 이 계약의 핵심이며, 새 테스트가 "이전에 만들어진 세션과 저장소 값도 읽힌다"와 "스테이징 값이 운영 항목을 읽거나 덮어쓰지 않는다"를 검사합니다.

## 4. 로그인 화면

- 전달하신 목업(`manee-login-remember-1.html`)은 이전 파일(`manee-login-remember.html`)과 **바이트 단위로 동일**합니다(이미지 포함). 이미 반영한 디자인이 그대로 기준입니다.
- 구조·간격·색·시스템 한글 글꼴·입력창·버튼을 반영했습니다. 색은 사장님 UI 토큰과 같은 값입니다(초록 `#16774C`, 글자 `#18342C`, 배경 `#F5F7F4`).
- **로고와 캐릭터는 기존 이미지 그대로**입니다. 목업의 두 이미지는 앱의 `MASCOT_IMG_DATA`, `MASCOT2_IMG_DATA`와 바이트 단위로 동일합니다(해시 일치).
- 구분은 **사장님 / 직원·매니저**. 양쪽 모두 "로그인 상태 유지"가 있고 기본은 체크입니다.
- 로그인·회원가입·비밀번호 찾기는 **기존 기능에 연결**되어 있습니다(`loginStoreOwner`, 사장님 `forgot-password-btn`/`store-signup-btn`, 직원·매니저 `data-staff-auth-action`). 기존 요소 ID를 모두 유지했습니다(테스트로 고정). 목업의 화면 확인용 처리는 가져오지 않았습니다.
- 오류(빈 값, 잘못된 비밀번호)는 입력창 아래 메시지로 보이고 해당 입력에 포커스가 갑니다. 눈 아이콘과 체크박스는 화면을 다시 그리지 않아 **입력하던 아이디·비밀번호가 지워지지 않습니다**. 아이디에서 Enter를 누르면 비밀번호로 이동합니다.
- 목업과 다른 점: ① `autocomplete="off"` 대신 `username`/`current-password`(브라우저 비밀번호 관리자 호환, 앱은 비밀번호를 저장하지 않음). ② 아이콘은 인라인 SVG. ③ 다크 모드는 목업 색값을 `prefers-color-scheme`으로 적용(앱의 다른 화면에는 다크 테마가 없어 로그인만 어둡게 보임).
- 320/360/390/430px, 사장님·직원 탭 모두 가로 넘침이 없습니다.

## 5. 사장님 홈 상태 표시 (보완)

색만이 아니라 **아이콘과 문구·사유**를 함께 보여 줍니다. 판정은 대시보드에 **이미 있던 조건만** 사용하고 새 기준을 만들지 않았습니다(자동 테스트가 임계값이 25와 40뿐임을 검사, 경계값 25·40은 "초과"만 해당).

| 상태 | 표시 | 조건 |
|---|---|---|
| 안정 | 초록 칩 + ✓ | 매출이 있고 아래 두 기존 조건에 해당하지 않음 |
| 관리 필요 | 빨강 칩 + ⚠ + 사유 문구 | **(v5, 대표 결정)** 인건비율 > 22% 또는 식자재비율 > 그 매장의 기준(기본 40%, 사장님이 매장별로 설정). 사유 문구는 저장된 기준을 따름("인건비율 22% 초과", "식자재비율 38% 초과") |
| 집계 전 | 회색 칩 | **매출보고가 하나도 입력되지 않음**(비율 판정 불가) |
| 매출 없음 | 회색 칩 | **매출보고는 입력됐지만 합계가 0원**(비율 판정 불가) |

- **비용 표시**: 집계 전·매출 없음인 매장에 인건비(출퇴근 기준 급여)나 지출이 있으면 "지출 120,000원 발생", "인건비 400,000원 · 지출 80,000원 발생"처럼 사실을 표시합니다. 이런 매장은 **초록 "안정"으로 처리하지 않고** 새 판정 기준도 만들지 않습니다.
- **합산과 개별 매장 분리**: 월 합산 카드에 "**합산 기준** 안정/관리 필요/집계 전/매출 없음"(합산 판정은 기존 조건 그대로)과 별도로 "**관리 필요 N곳**"과 그 매장 이름, "집계 전 N곳", "매출 없음 N곳"을 함께 보여 줍니다. 합산이 안정이어도 개별 매장 문제가 가려지지 않습니다. 판정된 매장이 하나도 없으면 "관리 필요 0곳"은 초록이 아닌 회색으로 표시됩니다.
- **사장님 화면에만 적용**합니다. 본사·프랜차이즈 대시보드의 기존 표시(빨간 점)는 그대로입니다.
- 색 대비: 안정 5.5:1, 관리 필요 6.1:1, 회색 5.6:1(모두 4.5:1 이상).
- 가상 데이터 확인: 인건비율 40% 매장 → 관리 필요, 식자재비율 45% 매장 → 관리 필요, 정상 매장 → 안정, 입력 없음 → 집계 전(지출이 있으면 지출 표시), 매출 0원 보고 → 매출 없음(지출 표시), 합산은 "합산 기준 안정" + "관리 필요 2곳".

## 9. v3 보완 — GPT v2 코드 검토 반영 (각 항목: 원인 · 수정 · 검증 · 남은 한계)

원칙: 재현되는 실패 시나리오를 먼저 테스트로 만들고 수정 전 코드에서 **실제로 실패하는 것을 확인한 뒤** 고쳤습니다(R1·R3 재현 테스트 27건과 R2 재현 테스트 6건이 수정 전 코드에서 실패, R4는 헤더만 있는 digest와 값 변조가 성공하는 것을 직접 확인). 기존 출퇴근·매출·급여·개인정보·매장 데이터는 수정·삭제하지 않았고 모든 시험은 가짜 데이터로 했습니다.

### R1. 계정 전환 후 늦게 도착한 이전 계정 응답
- **원인**: `clearStaffAuthView`는 캐시만 비웠고, 이미 진행 중이던 조회는 요청 시작 시점의 계정을 확인하지 않아 늦게 완료되면 `loadDashboardData` 등이 결과를 다시 `state`에 저장했습니다. 관련 조회(직원·근태·매출·지출·거래처·고정 스케줄·예약·공지·급여 조정·체크리스트)도 같은 경합이 있었습니다.
- **수정**: 요청 세대(`maneeViewEpoch`, 로그아웃·강제 정리·로그인 계정 변경 때 증가)와 조회별 요청 순번을 두고, 결과를 반영하기 직전에 "시작 당시의 계정·세대·최신 요청인지"를 확인합니다(`maneeLoadGuard`). 오래된 응답은 폐기하며 화면·로딩 상태·후속 조회를 건드리지 않습니다. 고정 지출의 "전월 복사" INSERT와 체크리스트 기본 항목 초기화는 쓰기 직전에도 확인해서 오래된 요청이 쓰기를 시도하지 않습니다. 서로 다른 월의 응답이 거꾸로 도착해도 최신 요청의 결과가 남습니다.
- **검증(가짜 DB로 응답 지연 통제)**: A의 첫 직원 조회를 지연 → 로그아웃·B로 전환 → A 응답 도착 순서에서 B의 화면·데이터·로딩 상태가 바뀌지 않음(B가 먼저 완료된 경우, `clearStaffAuthView` 없이 표시 계정만 바뀐 경우 포함). 조회 함수 11종과 `loadAllForStore`, 월 역순 도착, 오래된 요청의 INSERT 금지.
- **한계**: 본사·프랜차이즈 전용 조회(`loadOwnerRequests` 등)와 로그인 직후의 매장 목록 조회는 이번에 다루지 않았습니다. 실제 지연 네트워크에서의 확인은 하지 않았습니다.

### R2. 한 탭의 토큰 갱신이 다른 탭의 로그인을 삭제
- **원인**: `maneeAuthStorage.setItem`이 저장할 때마다(토큰 갱신·매장 ID 저장 포함) 반대 저장소의 같은 키를 계정 확인 없이 삭제했습니다.
- **수정**: 명시적 로그인(로그인 시작 시 표시 → 첫 세션 저장에서만 소비)과 일반 갱신·로그아웃을 구분합니다. 반대 저장소는 **비어 있거나 같은 계정의 사본일 때만** 정리하고, 다른 계정의 세션·매장 선택값은 지우지 않습니다. 갱신은 반대 저장소를 절대 건드리지 않습니다. 로그인된 탭은 자기 저장소만 읽고, 로그아웃한 탭은 다시 로그인하기 전까지 다른 계정의 세션을 읽지 않습니다.
- **브라우저 검증(가상 백엔드, 토큰 만료 95초로 자동 갱신 유발)**: 탭 A(해제, 계정1)+탭 B(유지, 계정2) 로그인 후 A·B 각각 토큰 갱신 → 서로의 세션 유지, 반대 순서(B 먼저, A는 이미 열려 있던 로그인 화면에서 로그인)·갱신도 동일, A 로그아웃 → B 유지, B 로그아웃 → 둘 다 로그인 화면, 매장 ID는 각자의 저장소에만 저장·삭제.
- **검증**: 리뷰 시나리오(탭 A 해제 로그인 → 탭 B 유지 로그인 → A 갱신 → B 세션 유지)와 반대 순서, 같은 계정 재로그인 시 중복 정리, 고아 매장 ID 정리와 다른 계정 매장 ID 보존, 로그아웃 시 다른 계정 세션 보존, 매장 선택값 저장·삭제, 페이지 새로 로드 시 저장 위치 유지(신규 테스트 11건 + 옛 동작을 기대하던 기존 어댑터 테스트 갱신).
- **한계(v5 갱신)**: 이 항목의 시나리오는 v5에서 **브라우저당 한 계정 정책**으로 대체됐습니다(§11.2). 이전 문장("두 탭이 각자 계정을 유지")은 더 이상 동작이 아닙니다.

### R3. 조회 실패를 초록 "안정"으로 표시
- **원인**: 대시보드 조회가 `{data, error}` 중 `error`를 확인하지 않고 `data||[]`를 써서 실패와 0건을 구분하지 못했습니다. 지출 조회가 실패하면 지출 0원·식자재비율 0%로 "안정"이었습니다.
- **수정**: 판정 입력(직원·근태·매출·지출)의 오류·통신 실패를 기록(`loadFailures`)하고, 읽지 못한 입력으로는 비율을 계산하지 않습니다(0이 아니라 알 수 없음). 매장은 노란 "조회 실패"(아이콘·문구, "읽지 못한 항목: 지출 · 근태")와 **다시 시도** 버튼으로 표시하며 초록 "안정"이나 "집계 전"으로 보이지 않습니다. 읽은 입력만으로 기존 규칙이 깨진 것이 확실하면 "관리 필요"가 우선하고 실패도 함께 표시합니다. 합산은 조회 실패 매장을 제외하고 "합산 기준 확인 필요"·"조회 실패 N곳"·"이 매장은 합산에서 제외했어요"를 표시하며, 실패가 있으면 합산이 초록 "안정"이 되지 않습니다. 전월 매출 조회 실패는 "전월 대비 확인 불가"로 표시합니다. 정상적인 빈 결과는 실패가 아닙니다.
- **검증**: 매출·지출·직원·근태 각각에 대해 권한 오류·통신 실패·정상 빈 결과를 구분(리뷰 재현: 매출 성공 + 지출만 실패 → "안정" 아님), 합산 표시, 다시 시도 버튼(가짜 DB 테스트 33건 중 R3 관련 + 브라우저 확인).
- **한계**: 판정과 무관한 조회(체크리스트, 세금 안내 확인)의 실패는 판정에 영향을 주지 않도록 그대로 두었습니다. 다른 화면(직원관리·급여·매출 목록)의 조회 실패는 여전히 빈 목록으로 보일 수 있고 이번에 바꾸지 않았습니다. 전체 매장 조회 실패 시에도 "합산 매출 0원"이라는 숫자가 함께 보이지만 "합산 기준 확인 필요"·실패 안내가 함께 있고 비율은 "—"로 표시합니다(`owner-home-all-lookups-failed-390.png`). 본사·프랜차이즈 화면은 표시를 바꾸지 않았고, 조회에 실패한 비율이 0%가 아니라 "—"로 보이는 점만 다릅니다.

### R4. 백업 검증 도구의 잘못된 성공 판정
- **원인**: `verifyFolder`는 헤더만 있는 digest도 성공시키고, 해시 열을 쓰지 않으며, 새로 계산한 SHA-256을 이전 기준과 대조하지 않아 같은 행 수의 값 변조도 성공했고 로그를 덮어썼습니다.
- **수정**: `init`(최초 1회: 필수 18개 대상이 정확히 한 번씩 있는지, 파일·행 수, `digest-after.csv`로 내보내는 동안 변경 여부를 확인하고 `BACKUP_MANIFEST.json` 기준 해시를 기록, 이미 있으면 **거부**)와 `verify`(기준과 대조, 기준은 수정하지 않고 날짜 로그를 새로 만듦), `db-check`(지금 DB digest가 백업 시점과 같은지)로 나눴습니다. 성공 문구는 확인한 범위만 말하고 **"CSV 내용=DB 내용"과 "복원 가능"은 항상 "확인 안 함"**으로 표시합니다.
- **검증**: 헤더만 있는 digest, 필수 대상 누락·중복·초과, 잘못된 행 수·해시, 파일 누락, 같은 행 수의 값 변조, 기준 보존, 로그 신규 생성이 증거가 아님(테스트 18건).
- **한계**: 여러 쿼리로 나눠 내보내는 동안 데이터가 바뀔 수 있어 완전한 단일 시점 스냅샷이 아닙니다(`digest-after.csv`는 변경 감지용). CSV 내용이 DB와 같은지는 확인할 수 없습니다. 기준은 기준을 만든 시점의 파일을 신뢰합니다. **실제 대시보드가 내려주는 CSV 형식으로는 시험하지 못했습니다.**

### 11.1 비율 기준 (식자재 기본 40%·사장님 설정, 인건비율 22%)
- **범위**: 경고 표시(상태 칩·색·문구)의 기준만 바꿨습니다. 급여 계산식·시급·근무시간·매출·지출 금액·개인정보 로직은 바꾸지 않았고 보존 함수 해시 테스트(`owner-ui-regression.test.mjs`)가 통과합니다. "기준 초과(>)"일 때만 관리 필요이며 정확히 같으면 초과가 아닙니다. 조회 실패·미입력·매출 없음은 초록 "안정"으로 바뀌지 않습니다.
- **기준값 한 곳**: `LABOR_RATIO_LIMIT = 22`, `DEFAULT_FOOD_RATIO_LIMIT = 40`, `foodRatioLimit(store)`. 사장님 홈(상태 칩·색·"N% 초과" 문구), 사장님 월간 리포트(순수익 카드), 매니저 홈 요약이 모두 같은 함수를 씁니다. 옛 25%/35%/40% 하드코딩은 남아 있지 않다는 것을 테스트가 검사합니다. 직원(일반 스텝) 화면에는 원래 비율 표시가 없어, 없던 매출·급여 조회 권한을 추가하지 않았습니다.
- **저장 위치(기존 저장소 재사용 확인)**: 매장별 설정(영업일 기준 시간, 매니저 요약 표시)은 `public.stores`의 컬럼입니다. 같은 방식으로 `stores.food_ratio_threshold numeric(5,2) NULL`을 추가하도록 SQL을 준비했습니다(`food-ratio-threshold.sql`). **NULL = 미설정 = 기본 40%**이므로 기존 매장·업무 데이터를 UPDATE하지 않습니다(마이그레이션 자체가 기존 행을 바꾸지 않는다는 것을 테스트가 스냅샷으로 확인).
- **권한**: 읽기는 이미 매장 구성원(사장님·매니저·직원)이 볼 수 있는 `stores` 행 그대로(`can_view_store`). 쓰기는 `manee_set_store_food_ratio(store_id, threshold)` 함수(SECURITY DEFINER)만 하며 **해당 매장의 활성 사장님 멤버십**이 필요합니다. 컬럼은 직접 UPDATE 권한 목록에 넣지 않아 매니저·다른 매장 사장님은 직접 바꿀 수 없습니다. 범위 1~100(DB 제약 + 함수), 소수 첫째 자리 반올림, NULL이면 기본값으로 되돌림.
- **화면**: 사장님의 "더보기 → 매장 설정 → 식자재비율 경고 기준"(숫자 입력·저장·기본값으로). 잘못된 입력(비어 있음·0·100 초과 등)은 요청 없이 안내, 서버가 거절하면(사장님이 아님·함수 미준비) 저장 안 됨과 이유 안내, 저장 성공 후 홈 판정 새로 계산. 기준 조회 자체가 실패하면(컬럼 없음 42703은 "미설정"으로 취급) 그 매장은 "읽지 못한 항목: 식자재 기준"으로 표시되고 초록 안정이 되지 않습니다.
- **전체 요약**: 매장별 판정을 바탕으로 "관리 필요 N곳"을 보여 주고, **한 매장이라도 자기 기준을 넘으면 합산 상태는 관리 필요**입니다(전체 평균이 낮다고 숨기지 않음). 기본 40%를 모든 매장에 다시 대입하지 않습니다. 합산 식자재비율 숫자의 색은 "자기 기준을 넘은 매장이 있을 때" 빨강입니다.
- **검증**: 판정·문구 경계(22/22.1, 40/40.1, 38/38.1, 37.5), 매장별 기준이 다른 경우, 기준 조회 실패, 값 저장·초기화·잘못된 입력·서버 거절·계정 전환 중 저장 (`food-ratio-limit.test.mjs` 12건, `login-remember-and-status.test.mjs` 갱신). **로컬 PostgreSQL 대용(PGlite) SQL 시험 10건**(`food-ratio-threshold.test.mjs`): 마이그레이션이 기존 행을 바꾸지 않음, 사장님만 저장·수정·초기화, 다른 매장 사장님/매니저/직원/비로그인 거절, 범위 밖 값 거절(함수·DB 제약), 매장 분리, 구성원 3종이 같은 값을 읽고 비구성원은 못 읽음, 비파괴 롤백 후 저장값 유지·재적용 가능. 브라우저(가상 백엔드): 기본값(22/40), 매장별 기준 적용(B 24%→"식자재비율 24% 초과", D 50%→안정), 설정 화면 저장.
- **적용 순서(아직 적용하지 않음)**: 스테이징에서 `food-ratio-threshold.sql` → 확인 → 되돌려야 하면 `food-ratio-threshold-rollback.sql`(**비파괴**: 저장 기능만 끄고 컬럼·저장값은 유지, §12.3). 프런트는 컬럼/함수가 아직 없어도 기본값으로 동작하므로 순서에 제한이 없습니다. 운영 DB의 `stores` 컬럼 권한이 스테이징과 다를 수 있어 적용 후 "구성원이 컬럼을 읽는지"를 확인해야 합니다(미검증).
- **한계**: 인건비율 기준을 사용자가 바꾸는 기능은 지시가 없어 만들지 않았습니다(22% 고정). 표시 소수(`toFixed(1)`)와 판정(원래 값) 차이는 기존과 같습니다. 본사·프랜차이즈 화면은 같은 매장 기준값과 22%를 쓰지만 별도 UI는 없습니다.

### 11.2 브라우저당 한 계정
- **정책**: 같은 브라우저 프로필·같은 앱·환경에서는 한 번에 한 계정만 로그인 상태입니다. "로그인 상태 유지" 체크 여부와 무관합니다. 다른 기기, 다른 브라우저 프로필, 시크릿 창, 운영↔스테이징은 저장소가 별개라 영향이 없습니다(한계로 명시).
- **구현**: `localStorage`의 작은 표식(`…active-account`, **계정 ID만**, 토큰 없음)이 "마지막으로 명시적 로그인한 계정"을 가리킵니다. 명시적 로그인이 성공하면 (1) 표식을 먼저 갱신, (2) 세션 저장, (3) 다른 저장소 영역의 세션·매장 ID 삭제. 다른 탭은 저장소 변화·창 포커스·탭 가시성 변화 때 자기 계정이 표식과 다른지 보고, 다르면 **자기 세션을 버리고 화면 데이터를 정리한 뒤 로그인 화면**으로 이동합니다(새 계정의 화면을 대신 보여 주지 않음, 새로고침 안 함). 해제로 로그인한 세션은 `localStorage`에 복사되지 않습니다.
- **밀려난 탭의 동작**: 토큰 갱신·지연된 요청·로그아웃이 새 계정의 세션·마지막 매장 ID·표식을 덮어쓰거나 지우지 않고(쓰기 거절, 로그아웃은 자기 것만 삭제, 표식은 같은 계정일 때만 삭제), 숨겨졌다가 다시 열려도 자기 세션은 버려져 되살아나지 않습니다. 밀려난 탭의 저장소 읽기는 비어 있도록 했으므로(어댑터 테스트로 확인), 그 탭이 나중에 `signOut`을 하더라도 새 계정의 토큰을 서버로 보내 폐기하지 못하게 설계했습니다(이 부분의 서버 쪽 동작은 실제 Auth에서 확인하지 못했습니다).
- **로그인 실패**: 비밀번호 오류 등 실패한 로그인은 어떤 저장소도 바꾸지 않고, 남은 "진행 중" 표시도 지웁니다.

## 13. v7 — GPT v6 재검토 V6-1: B 로그인 적용 중 A의 갱신이 먼저 저장되는 경합 (원인 · 수정 · 검증 · 남은 한계)

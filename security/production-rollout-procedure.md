**이 문서는 절차 확정본이며 실행 승인이 아닙니다.** 스테이징 시험(`staging-qa-checklist.md`)이 통과하고 별도 승인을 받기 전에는 운영 DB·Edge·앱·main에 아무것도 하지 않습니다. 모든 복구는 **기존 출퇴근·매출·급여·개인정보·계좌·매장 설정값을 삭제·초기화·덮어쓰지 않는** 방식입니다.

## 2. 적용 순서 (운영)

각 단계 뒤에 검증하고 실패하면 다음 단계로 가지 않습니다.

0. **게이트**: 스테이징 시험표 T1~T19 통과, 미검증 항목 0개 또는 명시적 위험 수용, 변경 이후 새 코드 검토 없음, 대표 승인.
1. **기준선 기록(읽기 전용)**: 게시 배포 ID·Edge 버전/해시·마이그레이션 목록·테이블별 행 수/해시(`backup-run.mjs`의 digest 또는 위 표의 조회).
2. **적용 직전 운영 독립 백업**: `backup → verify → rehearse → seal`(개인키는 별도 보관). `rehearse` 통과 전에는 "복구 가능"이라고 쓰지 않습니다. 사진(jsonb)이 복원되는지도 이 단계에서 확인됩니다.
3. **DB**: (a) `new-staff-self-profile-verify.sql` preflight = 문제 0 → (b) `new-staff-self-profile.sql` → (c) verify `applied` = 문제 0 → (d) `food-ratio-threshold.sql` → (e) 확인: `stores.food_ratio_threshold` 컬럼, RPC 실행 권한, 구성원이 값을 읽는지, **기존 행 해시(컬럼 지정)가 적용 전과 동일**. 기존 매장·직원·출퇴근 행을 UPDATE하는 문장은 없습니다.
4. **Edge**: `manee-staff-signup` 새 버전 배포(DB보다 먼저 배포하지 않음). 배포 후 `POST {"personal":{}}`가 새 버전 동작인지 확인(부작용 없는 요청).
5. **앱(main 병합)**: PR 병합 → 자동 production 배포. 병합 직전 `netlify api listSiteDeploys`로 현재 게시본이 6aabf130…인지 재확인, 병합 후 새 배포 ID를 기록.
6. **적용 직후 확인**: `/app-config.js`가 production(운영 ref), SDK 2.116.0 로드, 기존 사장님 계정으로 로그인해 대시보드 수치가 기준선과 같은지(읽기), 출퇴근·매출 화면 조회, 신규 화면(식자재 기준)은 **저장하지 않고** 조회만, 오류 로그 확인. 운영에서의 쓰기 시험은 별도 승인된 내부 시험 매장만.
7. 적용 후 24시간: 운영 데이터 digest 재비교(정상적인 실사용 변경은 허용, 예상 밖 감소 0), 문의·오류 감시.

## 3. 복구 순서 (실패 시, 비파괴)

**원칙**: 삭제·DROP·초기화·백업으로 덮어쓰기를 하지 않습니다. 되돌리는 것은 "새 기능 진입"이고 데이터는 남깁니다.

1. **호환 Edge를 가장 먼저**(`edge-rollback/manee-staff-signup-v1-compat.ts`): 이미 열려 있는 새 앱 탭이 구 Edge로 조용히 유실되는 것을 막습니다. 확인: 426 `app_update_required`.
2. **앱**: Netlify에서 이전 게시본 **6aabf130feb4820008bda06f 게시**(빌드 없이 즉시 되돌림). main 되돌림 커밋은 그 다음 필요할 때만(되돌림 커밋도 자동 배포됨).
3. **DB**: `new-staff-self-profile-rollback.sql`(테이블·컬럼·기존 행 유지) → `food-ratio-threshold-rollback.sql`(**RPC 권한만 회수, 컬럼·저장값 유지**). 두 롤백 모두 DROP·UPDATE·DELETE가 없고, 이전 앱은 남겨둔 컬럼·테이블을 쓰지 않아 무해합니다.
4. `catchup.sql`은 자동 복구에서 **실행하지 않습니다**(롤백 기간 승인 직원 처리는 별도 승인 절차).
5. 컬럼·테이블을 실제로 제거하는 정리는 별도 승인, 사전 읽기 전용 내보내기, 그리고 값 보존 확인 뒤에만.

## 4. 데이터 손실 사고 시 (백업으로 복구)

- 라이브 DB를 백업으로 덮어쓰지 않습니다. 봉인을 해제한 사본을 **격리된 DB(로컬 또는 새 빈 프로젝트)**에 복원하고(`rehearse`), 사고 전후를 대조해 **없어진 행만** 승인 후 되돌립니다. 값이 잘못 바뀐 사고는 변경 전후 대조로 필요한 항목만 복원합니다(런북 §3.4).
- 로그인 계정은 `auth.users`·`auth.identities`(비밀번호 해시 포함)가 덤프에 있으나 **Supabase로의 복원은 별도 검증이 필요**합니다. 세션·토큰은 복구 대상이 아니며 사용자가 다시 로그인합니다.

## 4-1. 백업 보관(접근 제한·암호화)

- 백업 폴더는 저장소·ZIP 밖에만 만들고(도구가 저장소 안 경로를 거부), Windows는 `icacls`로 현재 사용자만 접근 가능하게 제한합니다.
- 봉인: 공개키로만 암호화(`keygen` → `seal`), 개인키는 백업과 다른 곳(오프라인/비밀번호 관리자)에 보관. 개인키 없이는 복원할 수 없고, 개인키+백업이 함께 있으면 누구나 읽을 수 있으므로 함께 두지 않습니다. `--delete-plain`은 개인키로 시험 복호화에 성공한 뒤에만 평문을 지웁니다.
- 원본 DB 접속 정보는 환경변수로만 받고 도구가 명령줄·로그·보고서에 출력하지 않습니다.

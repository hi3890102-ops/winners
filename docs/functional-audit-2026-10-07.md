# 사장님·직원 앱과 관리자 웹 기능 점검

대상: `winners` 사장님·직원·매니저 앱, `manee-admin` 본사·프랜차이즈 웹. 가상 데이터와 별도 DB로 저장 실패·중복 클릭·계정/매장 전환을 재현했다. 운영 DB에서는 함수·권한·집계 상태만 조회했다.

## 발견하고 수정한 동작

| 흐름 | 수정 내용 |
| --- | --- |
| 출근·퇴근 | 위치 응답 대기 중 계정/매장이 바뀌면 요청을 보내지 않는다. 이전 계정의 늦은 권한 오류가 새 계정을 로그아웃시키지 않는다. 처리 중 버튼에 진행 상태를 표시한다. |
| 퇴근 후 근무 확인 | 서버 확인 실패 시 확인창과 입력 내용을 유지한다. 연속 확인·수정 요청은 한 번만 보낸다. |
| 근태 수정·확정·삭제 | 실패와 0행 응답을 성공으로 처리하지 않는다. 매장 ID를 함께 확인하고 성공한 서버 기록으로만 화면을 갱신한다. |
| 근무 시간과 급여 | 시간 수정 후 표시 시간과 초 단위 원본 시간을 함께 갱신해 급여 계산에 이전 시간이 남지 않게 한다. 기존 30분 단위 절사 방식은 유지한다. |
| 수기 출퇴근 | 직원·실제 날짜·시간 형식·같은 시작/종료 시간 입력을 검사하고 중복 등록을 막는다. 자정을 넘는 근무는 허용한다. |
| 월 이동·다른 휴대폰 | 과거 월 조회 중에도 오늘 근무와 미퇴근 기록을 조회한다. 홈에 다시 들어오거나 홈을 누르면 근태·스케줄을 갱신한다. 상시 실시간 구독을 추가한 것은 아니다. |
| 직원 정보·급여 조건·권한 | 저장 전에 성공 상태로 바꾸지 않는다. 같은 직원의 변경은 순서대로 처리한다. 급여·주 근로시간·날짜 입력을 검증한다. |
| 고정비 | 빈 값·문자·소수·범위 초과를 0원/정수 일부로 바꾸지 않는다. 0원과 환급 등 음수 정수는 보존한다. 연속 등록·삭제와 늦은 응답을 방어한다. |
| 매장 설정·고정 근무 | 서버 저장/삭제 실패 시 기존 표시를 유지한다. |
| 매출 보고 | 연속 제출을 막고, 저장 도중 매장이 바뀌어도 새 매장의 초안을 지우거나 체크리스트를 닫지 않는다. 저장 뒤 홈·보고서 집계를 다시 조회하도록 무효화한다. |
| 관리자 웹 | 문의·답변·편입 검토의 중복 요청과 계정 전환 후 늦은 화면 변경을 방어한다. 계정 상태 변경 0행 응답을 성공으로 표시하지 않는다. 관리자 변경은 별도 저장소에 반영한다. |

## 검증 근거

- 변경 전 기존 앱 검사: 657개 중 648 통과, 9 환경 의존 검사 건너뜀.
- 변경 후 로컬 앱 검사: 698개 중 688 통과, 10 건너뜀, 실패 0.
- 관리자 웹 검사: 16개 통과, 실패 0.
- 추가 재현 검사에서 수정 전 실패: 근태 14개, 업무 저장 13개, 매출 저장 3개, 관리자 9개. 이 숫자는 검사 수이며 독립적인 오류 개수를 뜻하지 않는다.
- 가상 PGlite DB에서 사장님의 근태 수정/확정 → 직원 조회/확인 → 사장님 재조회, 다른 사장님의 접근 차단, 이전 영업월 미퇴근 기록의 퇴근을 검증했다.
- CI에 별도 PostgreSQL의 12개 동시 출근·퇴근 요청 검사를 추가했다. 로컬에 PostgreSQL 서버가 없어 이 검사는 로컬 집계에서 건너뛰며, PR의 `Verify store-code release` 결과로 실행 여부를 판단한다.
- 앱·관리자 스테이징 및 운영 빌드, 인라인 JavaScript 문법 검사, `git diff --check` 통과.
- 운영에서 사용하는 주요 RPC 32종의 존재와 authenticated 실행 권한을 확인했다. 개별 데이터 접근 권한은 RLS와 함수 내부 검사로 제한한다.
- 운영 근태 1,683행을 조회한 시점에 같은 직원의 중복 미퇴근 그룹은 0개였다. 실시간 운영 수치는 이후 달라질 수 있다. 기존 기록을 수정하지 않았다.
- 실제 브라우저에서는 공개 로그인 화면, 빈 아이디 오류, 사장님/직원 역할 전환을 확인했다. 로그인 이후 화면은 이 점검에서 직접 조작하지 않았다.

`submitSalesReport` 보존 해시는 중복 제출·다른 매장 초안 보존·실패 시 입력 유지·저장 뒤 집계 무효화 회귀 검사를 추가한 뒤 해당 함수만 갱신했다. 매출 계산과 급여 계산 함수의 보존 해시는 그대로다.

## 남은 실기기 검증

로그인된 Android/iPhone에서 위치 허용·거절·GPS 오차, 실제 터치, 앱 백그라운드 복귀, 사진 업로드, PDF/엑셀 다운로드를 별도 테스트 계정으로 확인해야 한다. 자동 검사 통과를 모든 기기에서 오류가 없다는 의미로 해석하지 않는다. 운영 출퇴근·급여·매출을 시험 삼아 저장하거나 실제 알림을 발송하지 않았다.

보안 어드바이저에서는 정책 없는 비공개 내부 테이블 11개(INFO), 인증 사용자 실행 가능 SECURITY DEFINER 함수 3개(WARN), 유출 비밀번호 차단 미설정 1개(WARN)가 확인됐다. 함수 3개는 운영 정의에서 매장 소유자/본사 관리자 검사와 빈 search_path를 확인했다. 이번 UI 점검에서 인증 설정을 바꾸지 않았다. 참고: [Supabase 함수 점검](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [비밀번호 보호](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
